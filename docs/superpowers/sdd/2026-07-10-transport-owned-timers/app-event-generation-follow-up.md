## Problem

Runtime-directed app events carry only `SessionEvt.session_index`, which is a
pool slot. `SessionAppRuntime::drain_tx_events_to` resolves that slot to the
currently attached `SessionId` generation when the event is consumed.

After an old session is removed and its slot is reused, a delayed or duplicate
`Close` or `TxDeq` event from the old `AppSession` can therefore target the
replacement session. The transport pool and typed Session Lifecycle cannot
reject the event because its original generation was not retained.

This predates #41 and changing the app/session event format is explicitly out
of scope for the transport-owned timer refactor. It does not block TCP timer
ownership, but it does block describing the complete app/session lifecycle as
generation-safe.

## Desired Behavior

Runtime-directed app events retain enough identity to validate the original
generation before dispatch. An event emitted by an old app session must never
close, schedule, or otherwise mutate a replacement session that reused the
same pool slot.

## Acceptance Criteria

- [ ] App-to-session events carry or resolve an equivalent generation-safe
      session identity across Local and SVM/cross-process backends.
- [ ] A delayed old `Close` after slot reuse is ignored and leaves the
      replacement session Active.
- [ ] A delayed old `TxDeq` after slot reuse does not schedule the replacement
      session.
- [ ] The event ABI/versioning and shared-memory compatibility impact is
      documented.
- [ ] Existing Local and SVM app/session tests continue to pass.

## Reproduction Test Shape

1. Attach an app session and queue two Close events from it.
2. Consume the first Close and complete removal of the old SessionEntry.
3. Insert and attach a replacement session in the reused pool slot.
4. Consume the second old Close.
5. Assert that the replacement generation remains Active and receives no
   close notification.
