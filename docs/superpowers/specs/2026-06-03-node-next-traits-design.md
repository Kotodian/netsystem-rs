# Node Next Trait Design

## Context

The dataplane currently has several shapes for a node's next edge:

- Static enum-indexed next arrays generated by `#[hammer_component_macros::node_next]`, such as `IpInputNext`, `IpLocalNext`, `IpReassemblyNext`, and `RouteMatchNext`.
- Single dynamic next nodes stored directly on a node or control-plane snapshot.
- Runtime tables, such as protocol dispatch in `IpLocalSnapshot` and ICMP type dispatch in `IcmpInputSnapshot`.
- FIB/DPO lookup in `IpLookupNode`, where the next node is derived from forwarding state and has a cached/vectorized fast path.

The existing `NodeNext` trait is useful for enum slots, but it only describes static next labels. It does not describe where next nodes are stored or how a node decides the next node for a packet.

## Goal

Add trait boundaries that make new dataplane nodes easier to build while preserving the existing performance model:

- Keep static next enums compact and compile-time checked.
- Let fixed tables, single next nodes, runtime snapshots, and lookup-derived nexts share a common vocabulary.
- Reuse common speculative, rewrite/grouping, and vector enqueue flow where it fits.
- Give dynamic next nodes a persistent cached next seed when their output shape supports it.
- Avoid trait-object dispatch in hot packet paths.

## Non-Goals

- Do not replace the packet graph runtime.
- Do not force every node into one universal next abstraction.
- Do not remove specialized prefetch, cache, or vector paths from lookup-heavy nodes.
- Do not rewrite all nodes in one change.

## Proposed Traits

Keep the existing static slot trait:

```rust
pub trait NodeNext: Copy + Eq {
    const COUNT: usize;

    fn slot(self) -> usize;
}
```

Add a storage-oriented trait for components that can return a `NodeId` for a key:

```rust
pub trait NodeNextStorage<K> {
    fn next(&self, key: K) -> NodeId;
}
```

Expected implementations:

- Static next tables: key is a generated `NodeNext` enum.
- Single next storage: key is `()`.
- Protocol or ICMP tables: key is `IpProtocol`, `(IpVersion, u8)`, or a local newtype.
- Snapshots: implement the trait directly when the snapshot is the natural storage boundary.

Add a packet-resolution trait for nodes or helper structs that can decide a next node for one buffer index:

```rust
pub trait PacketNextResolver<G> {
    fn next_for_index(
        &self,
        runtime: &DataPlaneRuntime<G>,
        index: BufferIndex,
    ) -> CoreResult<NodeId>;
}
```

This trait should be used with generics, not `dyn PacketNextResolver`, in dataplane hot paths so the compiler can inline the resolver.

## Batch Processing Helpers

Introduce helper entry points above `NodeNextEnqueue`, `NodeNextFrames`, and `NodeNextVectorEnqueue`:

- `process_cached_speculative_next`: for nodes where packets can be validated against a speculative next, and non-matching packets are split into separate frames.
- `process_cached_rewrite_next`: for nodes that rewrite the current frame around one current next and schedule mismatches through `NodeNextFrames`.
- `NodeNextVectorEnqueue`: remains the specialized path for lookup-heavy nodes that already use cached vector decisions.

These helpers should remain thin wrappers. They should not hide prefetch details that materially affect performance.

The lookup node should remain on the vector path because it already combines FIB prefetch, `cached_next`, and batch chunking. ICMP-style nodes can use the cached speculative path. Local receive nodes can use the cached rewrite path. `IpInputNode` keeps its hand-tuned batch-prefetch chunking, but now seeds from and updates a persistent cached next.

## Macro Integration

Keep `#[hammer_component_macros::node_next]` as the way to define static next enums.

Extend macro-generated next enums only if it removes boilerplate without making generated code hard to reason about. For example:

- Continue generating `COUNT`, `VARIANTS`, `slot`, and `nodes`.
- Continue implementing `NodeNext`.

Avoid changing `#[hammer_component_macros::node]` first. Let nodes opt into the new traits manually, then decide whether macro support is worth it after two or three migrations.

## Migration Order

1. Add the traits and helper functions in `hammer-adapter::node::next`.
2. Add tests for static table storage, single-next storage, and speculative helper behavior in `hammer-adapter/tests/node_runtime.rs`.
3. Migrate `IcmpInputNode` first because it already uses a snapshot/table resolver and `NodeNextEnqueue::validate_frame_with_first_next`.
4. Migrate `IpLocalNode` and `IpReceiveNode` to the cached rewrite helper.
5. Migrate `IpInputNode` next while preserving its batch-prefetch path manually.
6. Convert static `node_next` array dispatches to `NodeNextStorage` where this improves consistency.
7. Leave `IpLookupNode` specialized unless the vector helper is proven to keep the current prefetch and cache behavior clear.
8. Treat `IpReassemblyNode` separately: it can emit multiple fragments for one input when a reassembly fails, so a one-next-per-index resolver helper is not a clean fit.

## Error Handling

Resolvers should keep existing behavior:

- Packet parse and validation errors still set node error codes on buffers.
- A resolver should return the configured drop/default/punt next when that is current behavior.
- Internal consistency errors, such as mismatched decision counts or frame capacity overflow, remain `CoreError::internal`.

The helper layer should be responsible only for frame splitting, scheduling, and cleanup on error.

## Testing

Add focused tests before migrating service nodes:

- Static enum next storage returns the expected `NodeId`.
- Single-next storage returns the same `NodeId` for `()`.
- Speculative helper keeps same-next indices on the current frame and schedules split frames for other nexts.
- Rewrite helper groups by cached next and schedules mismatched nexts.
- Runtime snapshot storage returns registered nexts and configured defaults.
- Error from a resolver cleans up newly allocated frames.
- Migrated `IcmpInputNode` keeps existing behavior in `crates/hammer-service/tests/icmp_input_nodes.rs`.

Run at least:

```sh
cargo test -p hammer-adapter
cargo test -p hammer-service --test icmp_input_nodes
```

If `IpInputNode`, `IpLocalNode`, or `IpLookupNode` are migrated later, run their crate-local node tests as well.

## Static Table Implementation

Use a const-generic blanket implementation for static arrays:

```rust
impl<K: NodeNext, const N: usize> NodeNextStorage<K> for [NodeId; N] {
    #[inline(always)]
    fn next(&self, key: K) -> NodeId {
        self[key.slot()]
    }
}
```

This avoids unstable generic const expressions such as `[NodeId; K::COUNT]` in the impl target. The generated `nodes` constructor from `#[hammer_component_macros::node_next]` remains the preferred way to build exact-size static next arrays, so normal node construction still gets compile-time size checking.

If a manually built array is too small, indexing will panic. That is acceptable for the initial trait because existing generated node constructors already use exact-size arrays; add a checked wrapper only if manual static next arrays become common.
