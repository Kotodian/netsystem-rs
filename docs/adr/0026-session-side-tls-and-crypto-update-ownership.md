# Session-side TLS and Crypto Update Ownership

The trusted Hammer daemon terminates application-selected TLS at the App/Session Seam through a session-side TLS plugin, rather than in `hammer-app` or inside generic Session Runtime. Hammer retains one payload-agnostic `AppSession` abstraction at every level of the App Session Stack. App connection policy fixes the Stack when constructing the connection; it is not a mutable mode inside `AppSession`.

Without TLS, the chain contains one `AppSession` between the external App and the selected transport. `session::ProtocolChain<P, L>` owns the App-facing `AppSession`, one concrete protocol state, and its complete lower chain. With TLS, the chain owns an ordinary lower `AppSession` whose FIFOs contain TLS records and a TLS protocol state that receives only the adjacent source and destination FIFO borrows. Its upper `AppSession` carries the immediately higher layer's protocol data. Both levels reuse the same `AppSession` implementation. `AppSession` does not interpret its data or own TLS state, and Hammer does not introduce a TLS-specific Session type, FIFO type, or Session wrapper.

The plugin consumes only adjacent transport-neutral FIFO borrows and requires ordered reliable stream semantics; it neither receives an `AppSession` nor accesses any concrete transport implementation. The Protocol Chain owns ordered traversal and publishes Session events from the FIFO positions reported by each successful protocol operation. The TLS plugin owns TLS Profiles, wire grammar, record state, authentication rules, and its `crypto::exchange::Protocol` implementation. The Main Thread Crypto Engine owns algorithm catalogs, Key Handles, and creation and advancement of handshake Exchanges, but it never sees Sessions, Data-Plane Buffers, or transport scheduling. Data Workers parse and reassemble handshake content before handing owned content to the Main Thread; Buffers remain worker-owned.

Each owning Data Worker retains its thread-bound traffic Crypto Contexts and invokes them synchronously from the TLS record path. Worker Key Provisioning is internal to the Crypto Engine: TLS passes only Key Handles plus connection and key generations, never raw traffic-key material. Runtime catalog updates are additive and failure-atomic: every worker prepares a candidate epoch before Main Thread publication under Barrier Synchronization, activates it before resuming packet dispatch, and acknowledges completion; existing Contexts remain bound without migration or fallback. TLS traffic-key updates are ordered only with the owning connection and never require an all-worker barrier.

The TLS record path is a FIFO-to-FIFO transform, not a Data-Plane Buffer transform. TLS borrows readable segments from the source App Session FIFO, asks its worker-local Crypto Context to write directly into reserved segments of the destination App Session FIFO, and publishes the destination bytes only after the complete record succeeds; source consumption occurs only with that successful publication. This permits one cryptographic transform write without an intermediate `Vec`, TLS-private Buffer, or FIFO-to-Buffer-to-FIFO copy. Data-Plane Buffers are allocated only when Session Runtime packetizes the lower Session for the Packet Graph, preserving lower-Session TX retention and transport recovery semantics.

This decision requires one generic `hammer-infra::Fifo` capability that the current read-only `peek_segments` interface cannot provide: writable segment reservation followed by explicit commit or cancellation. Reservation must not advance the visible tail, cancellation must leave FIFO contents unchanged, and commit must publish only initialized bytes. The capability belongs to generic FIFO infrastructure and must contain no TLS, Session, or transport concepts; its Rust interface and implementation remain a separately approved change.
