# Session-side TLS ownership through rustls

Status: accepted; supersedes ADRs 0017 through 0025

The trusted Hammer daemon terminates application-selected TLS at the App/Session Seam through an App Session protocol plugin, rather than in `hammer-app`, generic Session Runtime, or a Transport plugin. Application policy fixes protocol order when listening or connecting; the order is not mutable state inside `AppSession` or Session Worker.

Every Session independently owns RX/TX FIFOs, Session state, a selected Session behavior, and a selected Application behavior. Constructing a TLS selection creates a concrete worker-owned TLS connection whose record stores the TLS-record Session Handle and the application-data Session Handle. The TLS plugin state, not Session Worker, retains that relationship. `AppSession` does not interpret its data or own TLS state, and Hammer introduces no TLS-specific Session type, FIFO type, or Session wrapper.

The plugin consumes only the two transport-neutral FIFO borrows supplied for one operation and requires ordered reliable byte-stream semantics. It receives neither an `AppSession` nor an entire Session and cannot access any concrete Transport implementation. Session Runtime publishes Session events from the byte counts reported by each successful protocol operation.

rustls owns the wire grammar, handshake state, transcript, authentication, key schedule, traffic keys, record buffering, and record protection. The Main Thread retains immutable `Arc<ClientConfig>` or `Arc<ServerConfig>` values. Each owning Data Worker constructs, exclusively owns, advances, and drops its concrete `rustls::Connection`. Session Runtime retains only the plugin registration and opaque protocol connection identity needed to invoke that worker-local state. Hammer has no Crypto Engine, Key Handle, Crypto Context, algorithm catalog, implementation registry, or traffic-key provisioning path.

One protocol invocation operates on the TLS-record and application-data FIFO pair owned by the two Sessions recorded in the TLS connection. The implementation borrows readable input segments and writes directly into an output reservation. Output commit precedes input consumption; an error leaves both visible FIFO positions unchanged. Session publishes the exact FIFO advancement. An edge-triggered RX/TX enqueue or dequeue event targets the exact Session whose behavior should run. When record ingress creates reverse-direction protocol output, Session posts a `ProtocolOutput` event for that exact Session instead of calling egress recursively.

The worker-local Session Message Queue is the only protocol-progress queue. `appsl-rx-mqs-input` drains external Application MQ events into it and wakes `session-queue`; `session-queue` resolves the event's session index directly in the worker-owned Session pool and invokes that Session's selected behavior. Pool slots are resolved in O(1), retaining ADR-0010's VPP-compatible stale index-only event window. One node dispatch processes a fixed event budget so self-producing protocol work cannot monopolize the worker loop.

Session Queue remains a VPP-style Input/Driver Node; Hammer's PreInput kind is reserved for nodes that must run before Input/Driver nodes, not for Session Queue itself. Every dispatch captures one monotonic `now`, updates all installed Transports before Session Message Queue drain, processes control before IO work, and flushes generated TX once at the end. This advances Transport-owned timer wheels even when no App event is pending. The Session Worker now uses VPP's adaptive `Polling`, `Interrupt`, and `Idle` states: `FileMain` owns one generation-safe, one-shot deadline per worker, and its callback only marks Session Queue interrupt-pending. Session Queue uses the current worker-local IO output count as Hammer's proxy for VPP's last-vectors metric when selecting the next state. Session owns neither the transport timer wheel nor timer kinds.
