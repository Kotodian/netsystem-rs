# QUIC Connections and Streams are Sessions

Status: accepted

Hammer follows VPP's connectable-listener model: every QUIC Connection is represented by one payloadless parent Session, and every QUIC Stream is represented by its own child Session. Applications use the Connection Session handle to open or accept streams, while stream payload flows only through Stream Session FIFOs; keeping the connection outside Session would require a parallel public identity and lifecycle API that VPP does not need.

The QUIC plugin follows Hammer's existing TLS Session App ownership model. A Main Thread authority owns Application-scoped immutable client and server configuration. Each lower connected UDP Session selects concrete worker-local QUIC state, and the static Session App callbacks advance that state from UDP Session FIFO events. The QUIC plugin introduces neither Graph Nodes nor a generic engine function table.

Each Data Worker owns one `Pool<Context>` shared by the QUIC Session App callbacks and QUIC `SessionTransport`. `Context` represents exactly one listener, connection, or stream; there is no macro-generated second Session App context pool. This follows VPP's single worker-local `quic_ctx_t` pool while allowing each Rust variant to retain only its role-specific state.

Configuration registration follows the TLS ownership surface but uses QUIC-owned types and identities. `QuicMain` stores generation-checked `ConfigId` entries associated with the registering Application and exposes `register_client_config`, `register_server_config`, and `remove_config`; QUIC does not reuse TLS configuration identities or publish configuration through UDP or generic Session structures. A removed registry entry does not invalidate immutable configuration already retained by an existing worker-owned connection.

The public QUIC `TransportConfig` contains exactly `connection_timeout`, `max_concurrent_bidi_streams`, and `max_concurrent_uni_streams`, corresponding to VPP's `transport_endpt_cfg_quic_t`. Both client and server configuration retain one such value alongside their role-specific trust, identity, certificate, and ALPN input. Quinn's remaining transport-engine knobs are validated plugin policy rather than an open Application configuration bag. QUIC DATAGRAM and 0-RTT remain disabled and have no configuration fields.

Configuration publication and removal occur through the serial Main Thread Binary API control boundary defined by ADR 0039. Data Workers are stopped by `WorkerBarrier` for the synchronous method dispatch. The barrier is the publication boundary; QUIC configuration storage does not add a lock or a second completion protocol.

QUIC differs from the one-lower/one-upper TLS layer because one lower QUIC relationship multiplexes an upper Session hierarchy. The same owning plugin therefore acts as the Session App over UDP and as the Session Transport for the Connection and Stream Sessions it publishes. Generic Session Runtime retains only Session identities, callback registration, and opaque transport indexes; UDP owns no QUIC policy or state.

The existing listen chain remains authoritative: `ApplicationSessionRequest::Listen` enters `SessionMain::application_listen`, registers the Application Listener, and then calls `SessionMain::listen`, which invokes the selected transport's `start_listen`. Its function type becomes `fn(SessionListenerId, ApplicationId, Option<u64>, SessionListenEndpoint) -> RuntimeResult<()>`. The first argument is the already-created outer listener; the next two preserve the VPP endpoint facts needed by a layered transport. UDP ignores the Application and configuration arguments because it owns neither fact. QUIC validates the Application-scoped configuration and creates its lower UDP listener without retaining Application policy in UDP.

`QuicMain` owns one built-in QUIC Application identity. The outer QUIC listener remains registered to the external Application, while the lower connected-UDP listener is registered to the built-in QUIC Application and selects the QUIC Session App. This matches VPP, where `quic_start_listen` calls `vnet_listen` with `quic_main.app_index`; it also prevents external Application detach or unlisten from acquiring ownership of QUIC's internal UDP listener.

The Main Thread Listener context links the outer QUIC `SessionListenerId`, lower UDP `ApplicationListenerId`, lower UDP `SessionListenerId`, and immutable server configuration. Listen setup is failure-atomic: after any failure it removes successfully created resources in reverse order, stopping the lower UDP Session listener, removing the lower UDP Application listener, and finally removing the QUIC Listener context. Unlisten uses the same dependency order. Established connections do not depend on listener ownership and survive listener removal.

Unlisten does not allow an accepted server connection to finish its handshake after its outer listener has been removed. While workers are stopped by the same barrier, it first stops the lower UDP listener, removes the lower Application listener, and removes the generation-checked Listener context. A worker-owned Connection context that has not yet published its upper QUIC Connection Session detects that invalid generation on its next RX or timer advance, closes its connected UDP Session, and cannot publish through the removed listener. Main Thread control does not mutate a Data Worker-owned context pool. Already-published Connection Sessions and their Streams survive unlisten.
